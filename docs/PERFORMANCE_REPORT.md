# QDPilot0001 Idle Ops — Phase 2 성능 보고서

- 측정일: 2026-11-25 (KST)
- 측정 호스트: **macOS 15.7.9 / Apple M1 (arm64) 개발 머신** — Raspberry Pi 및 운영 서버 실측이 아닙니다.
- 대상: `feature/phase2-core-evolution` (비교 기준 `main` `326709d`)

> 워크오더 원칙에 따라 이 문서의 수치는 "개발 호스트 실측"으로만 표기합니다. 운영 서버·Raspberry Pi
> 성능으로 인용하지 마십시오. 운영 반영 전 동일 하네스로 Pi에서 재측정이 필요합니다(9장).

## 1. 측정 구성

| 항목 | 값 |
| --- | --- |
| 서버 | `python3 -m server` (ThreadingHTTPServer, listen backlog 128), SQLite WAL |
| 기능 서버 | `127.0.0.1:8123`, 프리뷰 DB(최종 측정 시 캐시 36대 보유 · 매니저 수동 플레이 누적) |
| QA 서버 | `127.0.0.1:8124`, 임시 DB(1시간 soak) |
| 쓰기 경합 서버 | `127.0.0.1:8126`, 신규 DB에 초기 재화 5,000,000 시드(동시 구매·조회) |
| 비교 서버 | `127.0.0.1:8125`, main `326709d` worktree(신규 DB) |
| 하네스 | [`tools/qa_perf.py`](../tools/qa_perf.py) — 표준 라이브러리, 멀티프로세스 클라이언트 |
| 네트워크 | 로컬 루프백. `HTTP(S)_PROXY` 환경변수를 하네스가 무시(프록시 측정 방지) |

백분위는 각 요청의 `time.perf_counter()` 왕복 시간을 정렬해 계산합니다. `rps`는 실제 완료 요청 수/벽시계
시간입니다. 계약 위반은 응답 스키마 필수 키 누락, 메시지 null, 공개 응답의 내부 필드(actor/opId/backup)
노출을 검사합니다.

최종 수치는 개발용 탭·백그라운드 폴링을 모두 닫은 상태에서 다시 측정했습니다. 초기 측정 중에는 미리보기
화면을 열어 둔 dev 탭 30여 개가 8초 간격으로 계속 폴링·구매하고 있어 꼬리(p99)가 부풀려져 있었고,
아래 표는 그 영향을 제거한 값입니다. 보유 서버 수(2대 vs 36대)는 서버 계산이 티어별 산술 1회라 측정값에
유의미한 차이를 만들지 않습니다.

## 2. 공개 관전 부하

공개 엔드포인트 `GET /idle-ops/api/v1/state?since=<cursor>`를 관전자 수만큼 폴링했습니다.

| 관전자 | 간격 | 시간 | 요청 | HTTP | p50 | p95 | p99 | max | rps |
| ---: | ---: | ---: | ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 1s | 30s | 30 | 200×30 | 6.31ms | 7.01ms | 7.14ms | 7.15ms | 1.0 |
| 10 | 1s | 30s | 300 | 200×300 | 8.36ms | 12.11ms | 13.06ms | 14.74ms | 10.0 |
| 50 | 1s | 30s | 1,500 | 200×1500 | 10.21ms | 22.58ms | 31.31ms | 36.02ms | 50.0 |
| 100 | 1s | 30s | 3,000 | 200×3000 | 5.59ms | 14.96ms | 47.19ms | 63.98ms | 100.0 |
| 100 | 8s | 30s | 400 | 200×400 | 14.76ms | 52.35ms | 58.80ms | 60.13ms | 13.3 |

- 전 구간 계약 위반 0, SQLite lock 오류 0, 서버 RSS 11.9~22.7MiB.
- p50은 관전자 수와 무관하게 수~십 ms로 안정적입니다. TTL 1초 스냅샷이 같은 구간의 요청을 공유하기
  때문에 100명·1초(100 rps)에서도 DB 읽기는 초당 1회 수준입니다.
- 8초 간격의 p95(52.4ms)가 1초 간격보다 높은 이유: 1초 간격은 요청이 고르게 분산돼 캐시 갱신 비용이
  작은 반면, 8초 간격은 다수 클라이언트가 비슷한 시점에 캐시 만료를 맞아 동시에 재동기화를 트리거하는
  영향으로 보입니다(추정). 절대값은 모두 61ms 이하입니다.
- 100명에서 p99(47ms)가 p95(15ms)보다 긴 꼬리는 서버 계산이 아니라 멀티프로세스 클라이언트
  스케줄링과 측정 호스트 코어 공유의 영향입니다(같은 하네스로 main 대비 아래 2.1 참고).

### 2.1 공개 읽기 Before / After (main `326709d` vs feature)

main은 공개 GET마다 정산 결과를 SQLite에 씁니다. 같은 하네스(100명·1초 간격·30초)를 양쪽에 실행했습니다.

| 서버 | 요청 | HTTP | p50 | p95 | p99 | max | 서버 RSS |
| --- | ---: | --- | ---: | ---: | ---: | ---: | --- |
| main `326709d` | 2,800 | 200×2,783 + **타임아웃 17** | 2.88ms | 48.54ms | **2,059.25ms** | **7,826.10ms** | 4.7→19.0MiB |
| feature | 3,000 | 200×3,000 | 5.59ms | 14.96ms | 47.19ms | 63.98ms | 11.9→21.0MiB |

- main은 관전자 수만큼 쓰기 트랜잭션(`BEGIN IMMEDIATE` + fsync)이 몰려 직렬화 꼬리가 초 단위로
  늘어나고, 클라이언트 소켓 타임아웃으로 **17건이 응답을 받지 못했습니다**(status 0, `Operation timed out`).
- feature는 공개 GET이 SQLite에 쓰지 않고 TTL 스냅샷을 공유하므로 전 요청이 64ms 이내에 완료됩니다.
- feature의 p50이 main보다 조금 높은(5.6ms vs 2.9ms) 것은 스냅샷 복사·메모리 정산·직렬화 비용이
  요청마다 붙기 때문이며, 꼬리와 실패율 측면의 개선이 훨씬 큽니다.

## 3. 쓰기 경합 (동시 구매·관리자 조회)

신규 DB(초기 재화 시드) 서버(8126)에서 서로 다른 `opId`로 동시에 구매하고, 관리자 상태 조회를 병렬로
수행했습니다.

| 시나리오 | 워커×작업 | 요청 | HTTP | p50 | p95 | p99 | max | lock 오류 |
| --- | --- | ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 동시 구매(캐시) | 10×5 | 50 | 200×50 | 2.92ms | 29.31ms | 85.75ms | 116.57ms | 0 |
| 관리자 상태 조회 | 20×10 | 200 | 200×200 | 2.93ms | 31.61ms | 80.27ms | 126.93ms | 0 |

- 구매 50건은 서로 다른 opId로 모두 1회 적용(요청 수=성공 수). `BEGIN IMMEDIATE` 경합은 SQLite
  `busy_timeout` 안에서 직렬화되며 500/lock 응답은 없었습니다.
- 관리자 조회 max 126.93ms는 200개 동시 요청 중 한 건의 스케줄링 꼬리입니다. p95 32ms로 실사용
  (8초 폴링)과 무관한 수준입니다.
- 앞선 측정에서 구매 400 응답("not enough requests")이 섞인 값이 있었는데, 이는 오류가 아니라
  게임의 재화 부족 가드입니다. 최종 수치는 재화를 시드한 신규 DB에서 측정했습니다.

## 7. 측정 중 발견·수정한 문제

| 증상 | 원인 | 수정 |
| --- | --- | --- |
| 50~100명 부하에서 p99 40~100ms, 간헐적 ~1초 꼬리 | stdlib 기본 listen backlog 5 → SYN 드롭·재전송 | TCP/UDS backlog 128 (`cd936af`) |
| 하네스가 실제 서버보다 느리게 측정 | 샌드박스 `HTTP_PROXY` 경유 | 하네스에서 프록시 우회 |
| 단일 프로세스 클라이언트로 100명 재현 불가 | GIL·소켓 직렬화 | 멀티프로세스 뷰어 |

## 8. 해석

- 공개 조회는 스냅샷 캐시 덕분에 100명·1초 간격에서도 p95 한 자리~수십 ms 수준이며, DB 쓰기는
  관리자 액션에서만 발생합니다.
- 쓰기 경합은 10~20 동시 워커에서 500/lock 없이 처리됩니다. 관리자 액션은 사람이 누르는 빈도라
  실제 부하는 이보다 훨씬 낮습니다.
- 남은 꼬리의 대부분은 서버 계산이 아니라 클라이언트 프로세스 스케줄링입니다(멀티프로세스 클라이언트
  수만큼 호스트 코어를 공유).

## 9. 한계와 운영 전 확인

1. 모든 수치는 M1 개발 호스트 값입니다. **Pi(ARM, 저전력)에서는 CPU·메모리·p95가 더 높을 수 있습니다.**
2. 운영 반영 전 Pi에서 아래를 재측정하십시오.
   ```bash
   python3 tools/qa_perf.py public --base http://127.0.0.1:8124 --viewers 1  --seconds 300 --interval 1
   python3 tools/qa_perf.py public --base http://127.0.0.1:8124 --viewers 10 --seconds 300 --interval 1
   python3 tools/qa_perf.py public --base http://127.0.0.1:8124 --viewers 100 --seconds 300 --interval 1
   python3 tools/qa_perf.py public --base http://127.0.0.1:8124 --viewers 2  --seconds 3600 --interval 8 \
     --rss-pid <pid> --out soak.json
   ```
3. 실제 다중 네트워크(WAN) 지연, Nginx 경유 비용, 모바일 Safari 성능은 이번 측정 범위가 아닙니다.
4. 브라우저 FPS는 headless Chrome 기준입니다. 실기기 GPU·발열 상태에 따라 달라질 수 있습니다.

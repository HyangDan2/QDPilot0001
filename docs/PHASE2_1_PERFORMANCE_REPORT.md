- 측정일: 2026-11-25 (KST)
- 측정 호스트: **macOS 15.7.9 / Apple M1 (arm64) 개발 머신** — Raspberry Pi·운영 서버 실측이 아닙니다.
- 대상: `feature/phase2-core-evolution` (Phase 2.1, WO-01~10)
- 비교 기준: 같은 호스트의 Phase 2 측정([`PERFORMANCE_REPORT.md`](PERFORMANCE_REPORT.md), `bd63a75` 계열)

> 성능으로 인용하지 마십시오. Phase 2.1 코드의 Raspberry Pi 재측정은 아직 수행하지 않았습니다.

## 3. 공개 관전 부하 (Phase 2.1 재측정)

공개 `GET /idle-ops/api/v1/state?since=<cursor>`를 관전자 수만큼 폴링했습니다. Phase 2와 같은
하네스·같은 호스트이며, 1시간 soak가 끝난 직후 다른 부하 없이 측정했습니다.

| 관전자 | 간격 | 요청 | HTTP | p50 | p95 | p99 | max | lock 오류 | 계약 위반 |
| ---: | ---: | ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 1s | 300 | 200×300 | 4.84ms | 17.73ms | 19.63ms | 20.03ms | 0 | 0 |
| 100 | 1s | 3,000 | 200×3000 | 4.82ms | 28.41ms | 39.71ms | 50.43ms | 0 | 0 |
| 100 (반복) | 1s | 3,000 | 200×3000 | 4.65ms | 19.04ms | 34.16ms | 39.85ms | 0 | 0 |

- 100명 측정은 클라이언트 4프로세스(`--processes 4`)로 실행했습니다. 두 실행의 p95가 28.4ms와
  19.0ms로 갈리는 것은 클라이언트 프로세스 스케줄링·호스트 코어 공유에 따른 실행 간 변동이며,
  서버 오류·lock·계약 위반은 두 실행 모두 0입니다.
- Phase 2 기준선(같은 호스트, 100명·1초): p50 5.59ms · p95 14.96ms · p99 47.19ms · max 63.98ms.
  Phase 2.1은 p95가 한 실행에서 기준선보다 높고 다른 실행에서는 비슷하며, p99·max는 두 실행 모두
  기준선보다 낮습니다. 정상 요청 경로에 추가 I/O가 없는 변경(readiness·타임아웃·ops 인덱스)과
  일관된, 실행 변동 범위 안의 차이로 해석합니다.
- 계약 위반 검사: 필수 키(`serverTime`, `state`, `derived`, `cursor`) 누락, `message` 노출,
  공개 응답의 내부 필드(`actor`/`opId`/`backup`) 노출.
- 서버 RSS: 100명 실행 중 16.4→19.7MiB, 18.6MiB(실행 간 차이는 샘플 시점 차이).

### 3.1 쓰기 경합·관리자 조회

초기 재화 5,000,000을 시드한 신규 DB(8798)에서 서로 다른 `opId`로 동시 구매하고, 관리자 상태
조회를 병렬로 수행했습니다.

| 시나리오 | 워커×작업 | 요청 | HTTP | p50 | p95 | p99 | max | lock 오류 |
| --- | --- | ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 동시 구매(캐시) | 10×5 | 50 | 200×50 | 3.73ms | 45.15ms | 82.51ms | 86.60ms | 0 |
| 관리자 상태 조회 | 20×10 | 200 | 200×200 | 3.41ms | 32.09ms | 151.68ms | 175.26ms | 0 |

- Phase 2 기준선: 구매 p95 29.31ms · p99 85.75ms, 조회 p95 31.61ms · p99 80.27ms. 구매 p99·조회
  p95는 기준선과 같은 범위이고, 조회 p99는 200개 동시 요청 중 한 건의 스케줄링 꼬리로 커졌습니다
  (max 175ms, 8초 폴링 실사용과 무관).
- 구매 50건은 모두 1회 적용됐고 400/500 응답은 없었습니다(재화 시드 500만).
- Phase 2.1의 관리자 변경 직렬화(WO-07)는 `BEGIN IMMEDIATE` 앞단에서 op를 조정하지만, lock 오류
  0·전 요청 성공 조건은 그대로입니다.

  이미지를 5장 → 2장(idle·버그)으로 줄였습니다.

## 5. 1시간 서버 soak

- 구성: 공개 관전자 2명(8초 간격) + 관리자 `/state` 8초 폴링 1시간(2026-11-25 08:17~09:18 KST).
- 결과:

| 구분 | 요청 | HTTP 200 | p50 | p95 | p99 | max | RSS |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 공개 soak | 900 | 900 | 3.0ms | 4.8ms | 7.03ms | 10.9ms | 23.1MiB (719회 샘플, 최대도 23.1) |
| 관리자 폴링 | 451 | 451 | — | — | — | — | — |

- 계약 위반 0, SQLite lock 오류 0. 관리자 폴링은 상태 코드만 기록했습니다(전부 200).
- Phase 2 soak(공개 900회, p95 11.63ms, RSS 15.9MiB)와 같은 시간·같은 관전자 수 기준으로 비교하면

  없었습니다.

## 6. 1시간 브라우저 soak

`python3 tools/wo10_browser_soak.py --seconds 3600 --interval 60` (1440×900)

| 항목 | 값 |
| --- | --- |
| 실행 시간 / 샘플 | 3,600.4초 / 60회 |
| FPS | 최소 54 · 중앙 60 · 최대 60 (첫 샘플 54, 이후 59회 연속 60) |
| JS 힙 | 9.54MiB — 60회 모두 같은 값(브라우저가 양자화해 보고하는 값) |
| 콘솔 오류 | 0 |
| 가로 스크롤 | 0 |
| 지연 로딩 / manifest | 상태 4개(idle·run·attack·repair), 경고 0 |
| 최종 캡처 | `docs/screenshots/wo10/browser-soak-final.png` |

- 월드는 1시간 동안 레벨 1에서 1,880요청까지 진행했고, 마지막 애니메이터는 repair 루프였습니다.
- Phase 2는 47분에서 세션이 끝나 목표에 미달했습니다. 이번 실행은 3,600초를 채웠습니다.
- 힙 값은 양자화되어 "증가 없음" 이상의 해상도를 제공하지 않습니다. 장시간 누수 여부는 이 수치만으로
  단정하지 않고, 이벤트·스프라이트·파티클 상한(코드·테스트)으로 함께 보증합니다.

## 8. 한계

1. 모든 수치는 M1 개발 호스트 로컬 루프백 값입니다. 운영 Nginx 경유·WAN·실기 GPU는 미측정입니다.
2. Phase 2.1 코드의 Raspberry Pi 재측정(207 테스트 포함)은 수행하지 않았습니다. Pi 수치는 Phase 2
   `bd63a75` 기준입니다.
3. 브라우저 FPS·힙은 headless Chromium 기준이며 `performance.memory`는 Chromium 계열에서만 제공됩니다.
4. `limit_req`/`limit_conn`은 문서 권고만 있고 서버·Nginx에 적용하지 않았으며 부하 검증도 하지
   않았습니다.
5. soak 중 관리자 폴링은 `/state` 읽기만 수행합니다. 쓰기 경합은 3.1에서 별도 DB로 측정했습니다.
6. 1920 headless FPS(49~55)는 GPU 없는 소프트웨어 래스터 결과이며, 실기 디스플레이에서의 60Hz
   유지 여부는 확인하지 않았습니다.
